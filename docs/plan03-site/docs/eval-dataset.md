# 评测集设计（评什么）

> **评测集 = 「评什么」的样本资产**，与[评估器设计](/evaluator.html)（怎么判）互补：评估器是「阅卷规则 + 阅卷人」，评测集是「试卷题目」。本页借鉴美团评测中台的方法论，落到交易系统，覆盖**结果侧（决策评测集）**与**过程侧（过程评测集）**两类样本。

## 一、评测集与评估器的关系

| | 评测集（本页） | 评估器（[评估器设计](/evaluator.html)） |
| --- | --- | --- |
| 回答什么 | 评什么（样本数据） | 怎么判（判定逻辑） |
| 本质 | case 集合：输入 + 参考答案 + 场景 + 评价维度 | 证据 + 边界 + 判定 |
| 复用 | 一个评测集可被多个评估器从不同维度评 | 一个评估器可套到多个评测集上 |
| 类比 | 试卷题目 | 阅卷标准 + 阅卷人 |

两者配套：**没有评测集，评估器无题可判；没有评估器，评测集无人评分**。缺一，评测闭环就转不起来。

## 二、两类评测集

交易系统有两个评测对象，所以有两类评测集：

| | 决策评测集（结果侧） | 过程评测集（过程侧） |
| --- | --- | --- |
| 评的对象 | 因子 / 策略的历史决策 | 会话过程（推理/工具/协议） |
| 单条 case | 决策包 + 实际 T+N 结果 + 判决结论 | 会话输入/输出 + 过程判定 |
| 参考答案（GT） | 判决器用真实结果算（超额 / 配对 t / 分层胜率） | 会话评估官的评估器判定 |
| 产生方 | 数据管家（落库）+ 回测判决官（回填 verdict）；资产登记官蒸馏成三元组（下游记忆视图） | 会话评估官 + 评测平台 |

> 注意：结果侧的「参考答案」是**闭式、可机器验证**的（回测能算出 T+N 超额），过程侧的「参考答案」是**开放语义**的（评估器 LLM Judge）。这正是[评测与可观测](/eval-platform.html)分水岭在「评测集」这一层的体现。

## 三、单条 Case 结构

借鉴「单 case 要含完整任务定义」，两类 case 的结构如下：

**决策 case（结果侧）**：

```
{
  "decision_id": "dec_20260101_001",        // caseID
  "version": "v1.0",
  "输入": { "decision_pack": {...},          // 信号/进出场/仓位/风控门
            "regime": ["涨停家数<30", "beta高"],
            "date": "2026-01-01" },
  "参考答案": { "实际结果": "T+20 超额 -3.44%",   // GT = 判决器回填
                "配对t": -18.95,
                "判决": "rejected" },
  "评价维度": ["独立日超额", "配对 vs 随机对照", "分层胜率"],
  "场景标签": ["涨停", "beta高", "拥挤度高"],
  "口径隔离": { "adjust": "前复权", "limit": "涨跌停口径", "cost": 0.0015 }
}
```

**过程 case（过程侧）**：

```
{
  "session_id": "sesn_abc123",              // caseID
  "version": "v1.0",
  "输入": { "trace": [...],                  // 会话 span（四元 id + 三层语义）
            "任务": "诊断账户近3日表现" },
  "参考答案": { "判定": "bad",                // GT = 评估器判定
                "原因": "遗漏近3日约束" },
  "评价维度": ["推理质量", "工具效率", "协议合规"],
  "场景标签": ["复盘", "盘后", "多轮"]
}
```

## 四、评测集按用途分三集（过程侧）

过程评测集按用途分三类，**回归集不替代基准集，校准用独立样本**：

| 数据集 | 内容 | 用途 |
| --- | --- | --- |
| 业务基准集 | 覆盖代表性会话任务的样本 | 比较 prompt/skill/协议 版本效果 |
| 问题回归集 | 已确认问题与边界用例 | 验证修复、检查退化 |
| 评估器校准集 | 人工标注的正反与边界样本 | 校准规则与 Judge 判断 |

决策评测集（结果侧）同理可拆「回测样本集」（核心 regime 覆盖）+「反面清单回归集」（数据地雷、已知坑）。

## 五、分布：贴合真实 regime 分布 + 优先级金字塔

借鉴「评测集要贴合线上分布和真实风险」——交易系统的「线上分布」就是**真实市场 regime 分布**：

- **覆盖率 4 维度**：能力（策略/因子/大盘/盘中）× 场景（涨停/暴跌/横盘/轮动）× 难度（简单/复杂/边界）× 目标（效果/安全/成本/稳定性）。
- **优先级 = 业务频率 × 失败损失**：P0 核心高风险（涨停封死/停牌/涨跌停/T+1 违反、数据地雷）→ P1 高频场景（常规策略生成/对账）→ P2 长尾（极端 regime）→ P3 探索（新因子/新策略边界）。
- **按 regime 分层**：决策评测集要按涨停家数 / 大盘 beta / 拥挤度 / 换手率分位分层——这直接呼应[可观测平台设计](/observability.html)的「定向观测」，也是你「9 个信号都不 beat 随机篮」悬案的解法：**先分层，再下结论**。

::: warning 分桶规则是占位，待考证
本节与 6.2 的分桶边界（<30/30-60/60+、跌/平/涨、低/中/高等）是**示意占位，不是从校准数据推导的**。按「未经严谨考证的数据不用于决策」的铁律，这些边界在 883 天校准数据验证前，只能标「待考证」，不能当作已确立的规则。怎么确定见 6.2.1。
:::

## 六、决策评测集构建：独立日切片与 regime 打标

决策评测集（结果侧）的构建核心是两件事：**独立日样本怎么切**（样本单位）与 **regime 标签怎么自动打**（分层维度）。

### 6.1 独立日样本怎么切

原则：**以「日」为独立样本，不用交易笔数虚增自由度**（同日多股相关）。

```
① 时间窗口：覆盖多个完整周期（校准基线 2023-01-01 → 2026-08-25，883 个交易日）
② 信号时点：T 日收盘后触发（只用 T 日及之前数据，绝不看 T+1 及以后 = 前视偏置防护）
③ 入场：T+1 开盘价买入（前复权）
④ 出场：T+1+N 收盘（或按出场规则：stop = min(stop_px, open)、TP = max(tp_px, open)、
        同日 SL+TP 先算 SL、跌停封死 raw_high ≤ limit_down 则卖不出、顺延持有）
⑤ 超额：篮子收益 − 同期沪深300 beta
⑥ 合并：同日多信号/多股 → 合并为一个「当日篮子」样本（不拆成多笔）
⑦ 配对对照：每个决策样本配一个「同天随机等规模篮子」，供配对 t 检验
⑧ 最小样本：每个 regime 切片 n≥5 才统计；n<5 不报结论
```

**三条硬约束**：

- **前视偏置防护**：信号用 T 日收盘数据，入场 T+1 开盘，影子回放严格按此（oracle 测试把关）。
- **剔 beta**：超额对沪深300剔 beta，未剔 beta 的超额一律不认（那是 beta 不是 alpha）。
- **口径一致**：前复权、涨跌停口径、成本 0.15%、T+1，全程同一口径。

### 6.2 regime 标签怎么自动打

标签必须在**决策时点（T 日）**用「当时可得」的数据打，不能事后用 T+N 数据（否则前视偏置）；口径变更后标签整体重算。

| 维度 | 数据来源 | 打标方式 | 分桶（占位待考证） |
| --- | --- | --- | --- |
| 涨停家数 | 当日全市场涨停家数 | 确定性代码（0 LLM） | <30 / 30–60 / 60+ |
| 大盘 beta | 沪深300 当日涨跌幅 | 确定性代码 | 跌 / 平 / 涨 |
| 板块拥挤度 | 板块成交占比/换手 | 确定性代码（分位） | 低 / 中 / 高 |
| 换手率分位 | 个股换手率全市场分位 | 确定性代码 | 低 / 中 / 高 |
| 消息面强度 | 当日消息/公告 | 语义打标（EMBEDDING + LLM） | 无 / 弱 / 强 |

**打标策略**：规则可判的用确定性代码（0 LLM，稳定可复现）；语义的用模型打标，低置信标「待考证」、不参与分层。

**版本化**：regime 标签与口径版本绑定（如 `regime:v1 = 涨停家数分桶 <30/30-60/60+`），口径变了标签重算、评测集重新分层。

#### 6.2.1 分桶边界怎么确定（数据驱动，禁止拍整数）

分桶边界必须从 883 天校准数据反推，两条路 + 一条校验：

1. **等频分位（首选）**：按样本量等分（如三分位），保证每桶 n≥5 可统计。换手率、拥挤度这类连续量，先三分位看单调性，再决定是否加断点。
2. **已验证断点**：只在「超额收益翻转点」设断点。例：拥挤度已校准为单调（低 −0.39% → 高 −2.20%），下一步是找超额从正转负的临界拥挤度，那个点才是断点。「<30/30-60/60+」这类整数断点，除非数据证明 30/60 是转折点，否则禁用。
3. **n≥5 校验**：每个分桶切片 n≥5 才纳入统计，n<5 合并相邻桶，不报结论。

**当前各维度的证据状态与下一步**：

| 维度 | 证据状态 | 下一步 |
| --- | --- | --- |
| 拥挤度 | ✅ 已校准（单调 低 −0.39% → 高 −2.20%） | 找临界断点（超额转负的拥挤度值） |
| 换手率 | ✅ 已校准（低换手 <5% 唯一中性桶） | 把 <5% 定为正式边界并验证 |
| 涨停家数 | ⚠️ 知识卡有「<30 唯一正收益区」论断，证据等级待确认 | 用校准数据验证 30 是否真为断点 |
| 大盘 beta | ✅ 必选（超额计算必须剔），非可选维度 | 定「跌/平/涨」的量化边界 |
| 消息面强度 | ❌ 无校准依据（占位） | 先验证是否有收益区分度，无则删除 |

- [x] 覆盖率「场景」维度的高频/高风险验证 → 🛠 框架已实现：`evalds.coverage`/`coverage_gaps`（能力×场景×难度×目标 四维计数 + 缺口），待真实样本接入。

> **已考证的 3 项共同结论**：三个维度都与 T+20 剔 beta 净超额**单调相关**，但所有桶仍为负
> ——涨停策略整体负超额，regime 区分的是「负多还是负少」，不是「赚还是亏」。方向一致：
> 「高涨停家数 / 涨市场 / 低换手」时负超额最小。相应 regime 标签版本 +1（`regime:v2`）。

**三态判定标准**（每项验证的结论只能是三者之一，禁止「搁置」当「待定」）：

| 态 | 判据 | 后续动作 |
| --- | --- | --- |
| ✅ 纳入 | 验证出与 T+N 超额有单调/可翻转关系，断点清晰，每桶 n≥5 | 分桶从「占位」升级「已考证」，regime 标签版本 +1 |
| ⚠️ 待定 | 数据不足无法下结论（样本太少 / 断点区间 n<5） | 不删除、不纳入；挂后续动作：延长样本窗 / 换数据源 / 降级为观察项，等样本积累后再验 |
| ❌ 删除 | 验证出与 T+N 超额无单调/可翻转关系 | 从候选清单删除，不再占位 |

### 6.3 回测样本集落库结构（duckdb DDL）

三条落库原则：**① 冻结快照保证 GT 可复现（前复权价会随除权调整，必须按决策时点冻结）② 分层可切片（regime 打散成列，直接 WHERE）③ 口径版本绑定（口径变了旧样本不混算）**。七张表：

```sql
-- ① 口径元数据（版本化，口径变了旧样本不混算）
CREATE TABLE caliber_meta (
  caliber_id    VARCHAR PRIMARY KEY,   -- 'caliber:v3'
  adjust        VARCHAR NOT NULL,      -- '前复权'
  limit_caliber VARCHAR NOT NULL,      -- 涨跌停口径
  cost_rate     DOUBLE  NOT NULL,      -- 0.0015
  code_format   VARCHAR NOT NULL,      -- '000001.SZ'
  eff_date      DATE    NOT NULL       -- 生效日
);

-- ② 决策事件（信号触发，T 日）
CREATE TABLE decision_event (
  decision_id  VARCHAR PRIMARY KEY,    -- 四元 id 贯穿
  session_id   VARCHAR,
  strategy_id  VARCHAR,
  factor_ids   VARCHAR[],              -- 抓手因子
  signal_id    VARCHAR,                -- 触发信号
  signal_date  DATE    NOT NULL,       -- T 日
  caliber_id   VARCHAR REFERENCES caliber_meta(caliber_id),
  trace_id     VARCHAR
);

-- ③ regime 标签（决策时点打标，绑定口径版本）
CREATE TABLE regime_label (
  decision_id  VARCHAR PRIMARY KEY REFERENCES decision_event(decision_id),
  limit_up_cnt VARCHAR,   -- 涨停家数桶 '<30'/'30-60'/'60+'
  beta_bucket  VARCHAR,   -- 大盘beta桶 '跌'/'平'/'涨'
  crowd_bucket VARCHAR,   -- 拥挤度桶 '低'/'中'/'高'
  turnover_q   VARCHAR,   -- 换手率分位 '低'/'中'/'高'
  news_level   VARCHAR,   -- 消息面 '无'/'弱'/'强'/'待考证'
  regime_ver   VARCHAR    -- 'regime:v1'
);

-- ④ 样本篮子（当日合并篮子 + 超额）
CREATE TABLE sample_basket (
  decision_id  VARCHAR PRIMARY KEY REFERENCES decision_event(decision_id),
  entry_date   DATE    NOT NULL,       -- T+1
  exit_date    DATE,                   -- T+N
  n_days       INTEGER,                -- N
  basket_ret   DOUBLE,                 -- 篮子收益
  bench_ret    DOUBLE,                 -- 同期沪深300
  excess_ret   DOUBLE,                 -- 剔 beta 超额
  cost_rate    DOUBLE,                 -- 实际成本率
  holdings     JSON,                   -- 个股明细（code/权重/entry/exit/收益）
  exit_events  JSON                    -- 出场事件（stop/tp/跌停封死顺延）
);

-- ⑤ 配对对照（同天随机等规模篮子）
CREATE TABLE paired_control (
  decision_id    VARCHAR REFERENCES decision_event(decision_id),
  control_date   DATE,
  control_ret    DOUBLE,
  control_excess DOUBLE,
  PRIMARY KEY (decision_id, control_date)
);

-- ⑥ 判决结果（判决器输出，只读生产）
CREATE TABLE verdict (
  decision_id      VARCHAR PRIMARY KEY REFERENCES decision_event(decision_id),
  excess           DOUBLE,
  t_stat           DOUBLE,
  paired_t         DOUBLE,
  layered_win_rate DOUBLE,
  verdict          VARCHAR,            -- 'rejected'/'accepted'/'unknown'
  regime_slice     VARCHAR,            -- 切片标识
  judged_at        TIMESTAMP
);

-- ⑦ 行情快照（冻结前复权，保证 GT 可复现）
CREATE TABLE price_snapshot (
  snapshot_id  VARCHAR,
  decision_id  VARCHAR REFERENCES decision_event(decision_id),
  trade_date   DATE,
  code         VARCHAR,
  open_adj     DOUBLE,   -- 前复权开盘
  close_adj    DOUBLE,   -- 前复权收盘
  high_adj     DOUBLE,
  low_adj      DOUBLE,
  limit_up     DOUBLE,   -- 涨跌停价
  limit_down   DOUBLE,
  bench_close  DOUBLE,   -- 沪深300 收盘
  PRIMARY KEY (snapshot_id, trade_date, code)
);

-- 切片查询索引
CREATE INDEX idx_signal_date ON decision_event(signal_date);
CREATE INDEX idx_regime      ON regime_label(limit_up_cnt, beta_bucket, crowd_bucket, turnover_q);
CREATE INDEX idx_code_date   ON price_snapshot(code, trade_date);
```

**历史快照怎么存**：`price_snapshot` 在**每个决策时点冻结一次**当日及之后 N 日的前复权价 + 涨跌停价 + 基准收盘。关键点——**前复权是「相对当前价」计算的，历史价会随每次除权调整**；如果不冻结快照，回看同一只票的历史超额会随除权漂移，GT 就不可复现了。所以 `sample_basket` 的收益、超额都从冻结的 `price_snapshot` 算，而不是实时重算。

**读写分工**：数据管家写 `caliber_meta / decision_event / regime_label / sample_basket / price_snapshot`（数据层）；回测判决官写 `verdict / paired_control`（判决，只读生产）；资产登记官读这三类产出蒸馏「意图-经验-效用」三元组。

## 七、构建：真实数据为主 + 合成补充 + 失败回流

| 来源 | 内容 | 路径 |
| --- | --- | --- |
| 真实数据（为主） | 数据管家落库的历史决策（decision_event + sample_basket + price_snapshot）+ 会话 trace | 决策执行 → 数据管家落库 → 判决器回填 verdict → 沉淀为评测集 case |
| 合成补充 | 因子变体（参数扰动）、regime 变体（不同市场状态）、边界 case | 按覆盖缺口生成 → 人工审核 |
| 失败回流 | Badcase（真实失败）、Disagree（人机分歧） | 复盘后回灌 → 版本化 |

> **决策评测集 vs 意图-经验-效用三元组 = 同一份历史决策的两个视图**，不是同一份东西，数据流向是单向的：**决策评测集（数据管家的原始表）是「样本视图」，供判决器回测/对账；意图-经验-效用三元组（资产登记官蒸馏）是「记忆视图」，供策略师效用检索**。流向：`数据管家落库 → 判决器回填 verdict → 资产登记官读两者蒸馏三元组`——评测集在上游，三元组在下游。

> 决策评测集的「真实数据」有一个天然优势：**每条历史决策的 T+N 结果都是市场给的、不可质疑的**——这比美团那边靠人工标注 GT 更硬，因为你的 GT 是判决器用真实成交算出来的。

## 八、GT 准新 + 环境隔离

- **GT 要准要新**：结果侧的参考答案必须是「判决器用真实结果算的」（T+N 超额 / 剔 beta / 配对 t），禁止模型自评冒充；口径变更（复权基准/涨跌停口径）后，旧 GT 立即失效重算。
- **环境隔离**：回测用**历史快照**（前复权、涨跌停口径、0.15% 成本），影子回放不污染生产数据；评测流量（trace 只读、写操作 mock/隔离）不写入生产库——这对应你「判决器物理隔离」在数据层的落地。

## 九、三类问题集：驱动两类进化

借鉴「根据人工标注沉淀三类问题集」，落到你的自进化闭环：

| 问题集 | 含义 | 驱动谁进化 |
| --- | --- | --- |
| Badcase set | 真实失败（因子失效/出场太慢/推理遗漏约束） | 策略/因子进化（回滚信号） |
| Disagree set | 判决器与对账官/人工不一致 | 判决器/评估器优化（校准） |
| Unknown set | 判决不出（证据不足/口径缺失） | 复核原因 → 补齐证据或标注待复核 |

这三类问题集就是[自进化设计](/self-evolution.html)里「归因 → 进化」的**素材来源**：Badcase 喂策略进化，Disagree 喂评估器校准，Unknown 喂数据/证据修复。

## 十、版本化与可追溯

每条 case 与评测集都版本化，保障可复现：**case 版本 · 评测集版本 · 评估器/评分器版本 · 被测对象版本（prompt/skill/协议/因子）· TraceId · 标注版本**。回测必须保持可比条件，否则分数提升可能只是数据集/标准/环境变化，无法说清业务能力是否真的提升。
